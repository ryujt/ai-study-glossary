# Model Monitoring (모델 모니터링)

> **모델 모니터링은 배포된 모델의 성능과 입력 데이터를 계속 지켜보며, 성능이 조용히 무너지는 순간을 잡아내는 활동이다.**

## 배포한 모델은 가만히 있어도 낡는다

소프트웨어 버그는 코드가 잘못됐을 때 터진다. 그런데 모델은 **코드가 그대로여도 시간이 지나면 틀리기 시작한다.** 세상이 변하기 때문이다. 코로나 이전 데이터로 학습한 수요 예측 모델은 코로나가 오는 순간 엉뚱한 답을 낸다. 모델 자체는 그대로인데 세상이 학습 시점과 달라진 것이다.

**모델 모니터링은 이 "조용한 노화"를 감시하는 계기판이다.** 자동차 계기판이 속도·연료·엔진 온도를 실시간으로 보여주듯, 모니터링은 모델의 정확도와 입력 데이터의 분포를 지켜보다 이상 징후에 경보를 울린다.

## 성능이 아니라 입력부터 감시하는 게 현실적이다

무엇을 지켜볼지는 크게 두 갈래다.

| 감시 대상 | 무엇을 보나 | 한계 |
|-----------|-------------|------|
| **성능 지표** | 정확도·정밀도·재현율·AUC 등 실제 성능 | 정답 레이블이 있어야 계산 가능 |
| **입력 데이터 분포** | 들어오는 데이터가 학습 때와 얼마나 다른가 | 정답이 없어도 즉시 측정 가능 |

현실에서는 정답이 한참 뒤에야 오거나 아예 안 오는 경우가 많다. 대출 상환 여부는 몇 달 뒤에 판명되고, 그때까지 성능은 계산할 수 없다. 그래서 **정답 없이도 지금 잴 수 있는 입력 분포 변화가 조기 경보로 특히 중요하다.**

여기서 두 종류의 변화를 구분한다.

- **[데이터 드리프트](Data_Drift.md)** — 입력 데이터의 분포가 학습 때와 달라진다. (예: 새 연령대 고객 유입)
- **[개념 드리프트](Concept_Drift.md)** — 입력과 정답 사이의 관계 자체가 달라진다. (예: 사기 수법이 진화)


## 흔한 오해

> ⚠️ **흔한 오해 — "테스트에서 성능이 좋았으니 배포 후엔 신경 안 써도 된다."**
>
> 배포 시점의 성능은 그 순간의 스냅샷일 뿐이다. 데이터가 흐르는 한 성능은 서서히 떨어질 수 있고, 모니터링이 없으면 사고가 터진 뒤에야 알게 된다. 모니터링은 선택이 아니라 [MLOps](MLOps.md) 순환의 필수 고리다.

## 정리하면

- 모델은 코드가 그대로여도 **세상이 변하면 성능이 떨어진다.**
- 성능 지표와 입력 분포를 지켜보되, 정답이 늦게 오는 현실 때문에 **입력 분포 감시가 조기 경보로 유용하다.**
- 변화는 입력이 바뀌는 데이터 드리프트와 관계가 바뀌는 개념 드리프트로 나뉜다.
- 이상이 잡히면 경보를 울리고 재학습으로 이어진다.
