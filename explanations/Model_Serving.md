# Model Serving (모델 서빙)

> **모델 서빙은 학습이 끝난 모델을 실제 요청에 응답하는 서비스로 띄워, 예측을 쓸 수 있게 내보내는 단계다.**

## 완성된 요리를 손님 테이블에 내는 일이다

주방에서 아무리 훌륭한 요리를 만들어도 손님 앞에 내놓지 않으면 소용이 없다. 학습을 마친 모델도 마찬가지다. 노트북 안 `.pkl` 파일로 남아 있는 모델은 아무에게도 예측을 주지 못한다. **모델 서빙은 이 완성된 모델을 서비스라는 테이블 위에 올려, 외부에서 요청하면 예측을 돌려주게 만드는 일이다.**

보통은 모델을 API 서버로 감싼다. 앱이나 다른 시스템이 데이터를 담아 요청을 보내면, 서버가 모델을 돌려 예측을 응답으로 준다.

## 실시간이냐 배치냐로 방식이 갈린다

모든 서빙이 즉답형은 아니다. 언제 예측이 필요한가에 따라 두 갈래로 나뉜다.

| 방식 | 언제 쓰나 | 예시 |
|------|-----------|------|
| **실시간 서빙 (온라인)** | 요청 즉시 한 건씩 응답해야 할 때 | 결제 사기 탐지, 챗봇, 검색 순위 |
| **배치 서빙** | 대량 데이터를 몰아서 주기적으로 처리할 때 | 야간에 전 고객 이탈 점수 갱신 |

실시간은 응답 지연(latency)이 생명이고, 배치는 한 번에 얼마나 많이 처리하는가(throughput)가 중요하다.

간단한 실시간 서버는 웹 프레임워크로 직접 만들 수 있다.

```python
from flask import Flask, request, jsonify
import joblib

app = Flask(__name__)
model = joblib.load("model.pkl")   # 학습된 모델을 미리 메모리에 올려 둔다

@app.route("/predict", methods=["POST"])
def predict():
    features = request.json["features"]
    pred = model.predict([features])
    return jsonify({"prediction": pred.tolist()})
```

실무에서는 이렇게 직접 짜기보다 TensorFlow Serving, TorchServe, [MLflow](MLflow.md) serve 같은 전용 서빙 도구를 쓴다. 버전 관리·배치 묶음·GPU 활용 같은 까다로운 부분을 대신 처리해 주기 때문이다.

## 흔한 오해

> ⚠️ **흔한 오해 — "모델을 배포하면 프로젝트는 끝난다."**
>
> 배포는 끝이 아니라 운영의 시작이다. 서빙 중인 모델은 트래픽이 몰리면 느려지고, 시간이 지나면 [데이터 드리프트](Data_Drift.md)로 성능이 떨어진다. 그래서 서빙 다음에는 반드시 [모델 모니터링](Model_Monitoring.md)이 따라붙는다.

## 정리하면

- 모델 서빙은 학습된 모델을 **실제 요청에 답하는 서비스로 내보내는** 단계다.
- 대개 API 서버로 감싸 클라이언트의 요청에 예측으로 응답한다.
- 즉답이 필요하면 **실시간 서빙**, 대량을 몰아 처리하면 **배치 서빙**을 쓴다.
- 배포는 끝이 아니라 모니터링·재학습으로 이어지는 운영의 시작이다.
